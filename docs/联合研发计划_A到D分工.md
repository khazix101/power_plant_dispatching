# Agent 调度与多站点联合调度研发计划

版本：2026-11-22  
适用范围：在现有单站直流微网滚动调度原型上，推进价格/调度 Agent 与多个站点的联合调度。  
排期口径：以下为相对周次；团队确认起始周后换算为日历日期。A-D 为责任角色，可映射到实际成员。

## 目标与边界

本阶段交付一个可复现实验原型，而非直接投产控制系统。原型覆盖 2-4 个站点、统一半小时调度步长、日前/滚动预测、站内储能和 EV/基础负荷、站点间共享功率或上级并网功率约束；站点拓扑、额定功率、储能参数和数据质量均须由实际资料确认。首版先实现集中式联合优化，待基准和通信边界稳定后再评估分布式/多智能体算法。

Agent 的首要决策边界是“价格档位 + 安全约束下的站内储能计划”，不允许直接绕开安全投影控制设备。价格响应须使用可追溯的需求模型；缺少真实价格响应数据时，结论标为仿真假设。多站点总目标、站间功率交换规则、共享线路约束和公平指标在第 1 周冻结。

## 现状与技术选型

- 已有 Python 单站滚动控制、直流潮流/能量结算、安全投影、价格响应、SOH/退化成本接口，以及 `src/game/rl.py` 中的 PyTorch 策略梯度/离散价格策略原型。
- 优化基线采用 Pyomo + HiGHS（`appsi_highs`）；兼容求解器由现有求解器工厂选择。数值运算和数据处理沿用 NumPy、Pandas；测试沿用标准库 `unittest` 和现有 `parper/test/run_paper_tests.py` 入口。
- Agent 第一版沿用 PyTorch，优先离散合法价格档位；以现有优化策略/确定性基线生成示范或 warm start，再做安全约束下的策略微调。暂不引入 Gymnasium、Ray/RLlib、微服务或新的数据库，除非第 1 周的运行与部署需求证明必要。
- 多站点第一版沿用 Pyomo + HiGHS 建立集中式协调模型；用站点索引扩展数据结构和约束。不得把各站单独求解后相加称为“联合最优”。
- 项目未发现统一依赖锁文件。本轮先由 A 记录 Python、Pyomo、求解器、NumPy/Pandas、PyTorch 的实际版本与可用性，形成运行环境清单，不在未核验前要求全员升级依赖。

## A-D 责任分工

### A：技术负责人、问题定义与接口/数据契约

**明确任务**

1. 第 1 周冻结场景边界和指标：站点数量与 ID、调度间隔、预测时域、站间交换含义、上级功率上限、价格范围、负荷优先级、储能 SOC/SOH、安全约束、系统目标和成本口径。
2. 建立统一数据 schema：时间戳及时区、站点静态参数、风光/负荷/EV 预测与实测、价格、SOC/SOH、站间联络线及限额、缺失值和来源字段；明确单位和正负号约定。
3. 定义站点策略和协调器 API、配置格式、结果 schema、失败/缺测状态和版本字段；把现有单站 `ForecastBundle`、滚动控制器、安全层对齐到该契约。
4. 维护架构决策记录、风险/依赖清单、周会决议及跨模块集成；确认模型假设有来源，不让缺失输入静默变成零值。

**技术栈与主要交付**：Python dataclass/JSON schema（若项目未引入 JSON Schema 库则先用可验证的 Python 数据类）；现有 NumPy/Pandas；`docs/multi_site_contract.md`、`docs/architecture_decisions.md`、环境版本清单和接口契约测试。

**验收方法**：至少 2 个站点样例可按契约加载；单位、时区、缺失值、重复时间戳、站点 ID 错误均有明确报错或状态；B/C/D 能仅依赖契约并行开发；字段变更有版本说明和回归测试。

### B：价格与调度 Agent

**明确任务**

1. 划清 Agent 观测、动作、奖励和 episode 边界。观测至少包含预测窗口、负荷/请求、SOC/SOH、备用裕度、上次价格/动作、时间信息和网络拥塞摘要；价格动作必须来自冻结的合法档位，储能动作经安全投影。
2. 建立固定价格、规则策略、当前滚动优化/BRI（如适用）作为基线；保证训练、验证、测试按日期或场景分割，禁止同一天数据泄漏到多个集合。
3. 用确定性优化结果做可选 warm start/行为克隆，再训练离散策略；至少 5 个固定随机种子，保存配置、模型权重、训练曲线和逐步决策日志。
4. 分阶段评估：先单站价格策略，再加入储能调度动作；价格与功率同时学习仅在消融说明两类动作各自贡献后进行。

**技术栈与主要交付**：Python、PyTorch、NumPy；复用 `src/game/rl.py`、`src/game/rl_env.py`、现有安全层与滚动环境；提交训练/评估脚本、配置和 Agent adapter，不复制一套独立物理环境。

**验收方法**：单元测试确认动作始终合法、安全投影生效、随机种子可复现、模型存取一致；在锁定测试集与相同预测信息/资产/初始 SOC/SOH 下，与固定价、规则、优化基线做配对回放。报告服务电量、未服务量、用户请求与响应、弃电、储能/网络损耗、退化成本、运营价值、约束违约率、投影率、运行时间和跨种子区间；任一硬约束违约不允许以奖励均值抵消。性能提升以预先冻结的运营价值目标和置信区间判定，不预设 Agent 必须胜出。

### C：多站点联合调度与协调器

**明确任务**

1. 整理站点级模型和站间耦合：上级并网/变压器总功率、共享线路/联络线限额、站点局部功率平衡、储能 SOC、可调负荷、站点电价和必要的公平/优先级约束。
2. 用现有单站模型抽象成可索引的 site component；实现集中式联合优化器，统一决定每站价格或需求响应目标、储能计划和站间交换功率。首版与各站完全独立运行基线比较。
3. 建立拓扑与设备限额配置接口；缺少实际线路参数时只运行明确标为合成数据的压力测试，不宣称工程可行或物理校核已通过。
4. 评估集中式模型规模、可行率、求解时间和瓶颈，提出第二阶段分布式协调（如 ADMM/多智能体）的触发条件和接口，但本阶段不把分布式算法列为验收前置项。

**技术栈与主要交付**：Python、Pyomo、HiGHS、NumPy/Pandas；提交多站点协调模块、2-4 站合成/脱敏样例、集中式配置与独立站点基线脚本。

**验收方法**：2 站和 4 站小例子均可求解；逐时检查站内和系统功率平衡、SOC/功率边界、站间限额及全局上限；通过手算小例和约束扰动测试（收紧线路/上限后结果应可解释变化）。报告 centralized 与 independent 两类方案的总成本/运营价值、服务、公平性、弃电、损耗、求解状态和时间；不可行状态必须保留并说明，不可静默退化为单站解。

### D：数据管线、仿真回放、基准测试与发布验收

**明确任务**

1. 盘点可用站点历史数据、时间覆盖、采样频率、单位、缺失率、设备参数来源和隐私限制，产出数据字典及质量报告；不把合成、预测和实测数据混称。
2. 建立统一多站滚动回放器：共同时间轴、相同起始状态和资产约束，接入 B 的 Agent 与 C 的协调优化器，保留逐时账本、输入快照、版本/哈希和失败状态。
3. 维护固定价、规则、独立站点、集中式联合调度等可比较基线；执行配对日期/场景测试和消融测试，输出机器可读汇总与图表。
4. 维护测试入口、集成流水说明和发布清单；发现接口或账本问题时提供最小复现，不私自修改 B/C 的策略定义。

**技术栈与主要交付**：Python、Pandas/NumPy、标准库 unittest；复用现有实验脚本与账本约定；提交数据审计脚本、回放入口、基准配置、测试报告和可复现实验 manifest。

**验收方法**：小规模合成案例的系统/站点能量账本残差低于项目冻结阈值（建议绝对值 `1e-6 kWh`，若求解器精度需调整须先记录决议）；所有方法使用相同输入、时段、资产和初态；随机实验固定种子且完整保留失败运行；一条命令可重跑 smoke suite，完整实验可由 manifest 重建。

## 共用验收指标与规则

- **物理与安全**：站内及系统功率平衡、SOC/SOH 边界、充放电功率、EV/基础负荷服务优先级、并网/站间线路限制；分别报告硬违约数、最大违约和安全投影率。
- **业务价值**：服务电量及服务率、未服务量、用户成本、实际交付电量对应收入、弃电、储能转换损耗、网络损耗、退化成本、净运营价值及计算时间。收益必须采用冻结的统一定义，不能用请求电量代替交付电量。
- **联合调度价值**：联合策略与独立策略在共同需求回放下配对比较；另报站点间服务公平性/成本差异，不能只报系统总和掩盖单站损害。
- **统计与复现**：按日期/场景切分；锁定测试集；Agent 至少 5 seeds；报告样本量、均值/分位数和置信区间。测试失败、求解器未收敛、输入缺失案例均保留在报告中。
- **当前证据边界**：现有多站点联合优化、真实站间联络线参数和可用于证明泛化的多站点实测数据尚未由当前代码清单确认。单站 Agent 原型和单站网络模型不构成这些能力已验收的证据；补齐前的结果标记为原型或合成场景。

## 依赖与协作节奏

- A 在 M0 指定最终需求负责人和业务价值口径；未能确认的价格响应、线路额定值、站点地理/电气关系以假设登记，不能自行填入“真实值”。
- B 依赖 A 的状态/动作 schema 与 D 的统一回放环境；C 依赖 A 的站点/网络 schema 与 D 的账本；D 不重定义策略奖励或优化目标。
- 每周一次集成评审，每个节点前提交可运行分支/变更、测试命令、结果摘要和已知失败。模块接口变更需 A 记录决议，受影响负责人更新契约测试。
- 代码验收以现有 Python 项目为主，不在本阶段拆分微服务；生产部署、在线下发价格、实时遥测接入和自动控制审批不属于本阶段交付。
